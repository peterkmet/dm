# Chaos Strikes Back support: implementation plan

Approved by the user on 2026-10-04 (design in chat, no PRD, as for the DM port). Branch: `feature/2026-10-04-csb-support`. Code style: `docs/coding-standard.md`.

## Goal

The C port plays Chaos Strikes Back (CSB, Amiga) from the user's own disks, in addition to Dungeon Master. A start screen in the DM font selects the adventure and the mode.

## Research

Read these documents before each step. They hold the addresses and the formats.

- `docs/csb-port-integration.md`: audit of the port, design of the selection screens.
- `docs/csb-engine-diff.md` and `docs/csb-appb-symbols.csv`: the CSB engine (`APPB.FTL`, disk A) against DM `KAOS.FTL`.
- `docs/csb-data.md`: CSB `Graphics.DAT`, `Dungeon.DAT`, save file, `ENDA.DAT`.
- `docs/csb-new-adventure.md`: `MINI.DAT`, the merge that builds `CSBGAME.DAT`. Prototype and differential test in `tools/csb/`.

## Decisions

- Data: `game/` stays DM. CSB disk A is in `game-csb/`, CSB disk B in `game-csb/disk-b/` (the disks have files with the same name and other content). Decompiled CSB modules: `decomp-csb/A/`, `decomp-csb/B/`. All are git-ignored. Tests that need CSB files skip when they are missing.
- Flow (user-approved):
  1. Adventure screen: DUNGEON MASTER / CHAOS STRIKES BACK. CHAOS STRIKES BACK is grey and cannot be selected when the CSB files are missing.
  2. Mode screen: VANILLA / ADVANCED / LLM. Escape goes back to the adventure screen.
  3. DM: the existing entrance. CSB: a text screen NEW ADVENTURE / RESUME / QUIT.
  - `--adventure dm|csb`. With `--adventure` and `--mode`, no selection screen. `--mode` alone means DM and no screen (existing scripts and tests keep working). `--adventure` alone shows the mode screen.
- The open decisions of `docs/csb-port-integration.md` take its proposals: Escape on the CSB screen goes back to the mode screen; Escape on the adventure screen does nothing; `--data DIR` is the disk A folder of the chosen adventure; the cursor does not wrap; the font comes from DM `Graphics.DAT`, else from CSB `Graphics.DAT`.
- Engine data: the port keeps its DM addresses. For CSB, `kaos_load` builds a KAOS-layout image from `game-csb/APPB.FTL`: it copies each table that the port reads from its CSB address to its DM address, and converts the tables with another layout (strides, split wall set ids, 6-byte action sets). The 25 files with `#define ... 0x10xxxx` do not change. Tables with other content or size (29 spells, experience gain) get an explicit CSB branch.
- New adventure: NEW ADVENTURE starts a new game in the CSB prison (`game-csb/Dungeon.DAT`, 24 mirrors). When the party saves in the prison (dungeon ID 12), the port merges the party into `MINI.DAT` (as `CEDT.FTL` does), writes `CSBGAME.DAT`, loads it, and the game goes on in the CSB dungeon. The original needs a restart with the utility disk; the port does not. Champion import from a DM save is out of scope.
- Copy protection: left out. The port acts as if every check passes.
- SAVE AND QUIT and the credits go back to the CSB screen, as the DM port goes back to the entrance.
- End of the game: wall sensor type 18 plays `ENDA.DAT`. If the animation format cannot be decoded completely, the step shows the decoded frames and documents the rest.
- Turn-based (LLM) mode: `new_game` over the socket starts NEW ADVENTURE (prison). The player recruits at the mirrors and calls `save`; the merge then happens as in the window.

## Steps

Each step ends with green tests (`make -C port`, `uv run pytest -q`), a review by the `reviewer` agent, and a commit. A fresh subagent executes each step. Mid-step decisions go into this plan or the research docs.

### Step 1: Adventure value and selection screens

- `port/src/adventure.c/h` and `port/src/select.c/h` as designed in `docs/csb-port-integration.md` (sections "The adventure value", "The selection module", "Argument parsing", "The game loop and the screen switch", "CSB entrance screen").
- `savegame.c` takes the file names from the adventure (`DMGAME.DAT/.BAK` or `CSBGAME.DAT/.BAK`). Quick save stays `QUICK.DAT`.
- Until Step 2 exists, NEW ADVENTURE and RESUME of CSB show "NOT AVAILABLE YET" on the CSB screen.
- Tests: `tests/test_select.py` (helpers, selection logic, drawing check, process exit codes). Existing tests stay green without edits.
- Decisions made during the step:
  - Font check: DM and CSB `Graphics.DAT` item 695 are the same 768 bytes. ASCII capitals (codes 65-90) draw correctly; `endgame_print_text` is not needed.
  - The CSB presence check uses the `--data` folder only with `--adventure csb`, else `game-csb/` (open decision 4 of `docs/csb-port-integration.md`). `build/dm --data game` does not disable CHAOS STRIKES BACK.
  - `start_adventure` loads the game data before `apply_mode` opens the control socket, so a load failure leaves no socket file.
  - `select_start_csb(message)` shows the CSB screen with an optional message line. `main.c` calls it with "NOT AVAILABLE YET" after NEW ADVENTURE or RESUME. The CSB screen and Escape stay in `MODE_SELECT`; `apply_mode` runs only when an adventure starts (DM entrance, or `--show`/`--view`).
  - `main` logs `adventure dm, mode <name>` when the DM entrance starts. The process tests use the line.
  - The screens use the system mouse pointer: the platform layer shows it until the game sets a pointer image.
  - Open for Step 5: after a CSB game ends, the CSB screen and Escape to the mode screen can change `g_game_mode` after `apply_mode` already ran (control socket open). Decide then whether Escape goes back to the mode screen after a game.

### Step 2: CSB engine image

- Data folder rule (decided after the Step 1 review): `--data DIR` sets the CSB folder only with `--adventure csb`. Without `--adventure`, `--data` applies to DM only, and CSB uses `game-csb/`. `main.c` computes the CSB folder once (`csb_dir`) and uses it for the presence check and for loading.

- `port/src/ftl.c` (or a new `port/src/csbimage.c`): with `g_adventure == ADVENTURE_CSB`, load `APPB.FTL` and build the KAOS-layout image. Use `docs/csb-engine-diff.md` "Data tables" and `docs/csb-appb-symbols.csv`. Generate the address list with a script under `tools/csb/` if that is simpler than writing it by hand; check the generated file in.
- `tables.c`: 6-byte action sets, CSB experience gain values, 29 spells (`SPELL_COUNT` per adventure).
- `gameloop_load_data` loads the CSB data folder. `--view` with `--adventure csb` shows the prison.
- Tests: every copied table equals the bytes at its CSB address; the tables that DM and CSB share have equal bytes in both images; the converted tables match the documented layout; `gameloop_load_data("game-csb")` succeeds; a new game in the prison renders the view without errors.
- Decisions made during the step:
  - `port/src/csbimage.c` holds the address table `csb_copies` by hand, one row per table part, with the CSB name in a comment. Most addresses needed a code reading, so a generator script was not simpler. `tests/test_csb_engine.py` checks every row against `APPB.FTL` and, for equal tables, against `KAOS.FTL`. The new addresses and their code references are in `docs/csb-engine-diff.md` "Engine selection and table addresses".
  - `kaos_load` checks `g_adventure`: for CSB it loads `APPB.FTL` and calls `csb_image_build`. `adventure_engine_name()` gives the file name. `tests/test_tables.py` builds `tables.c` and `ftl.c` alone, so its source list now also has `adventure.c` and `csbimage.c`.
  - Spells: the 29 CSB spells are at `CSB_SPELLS` (`0x104160`, after the KAOS data). `spells.c` (`spell_count`, `spells_address`) and `tables.c` read 25 or 29 spells by adventure. Until Step 7, a cast of spells 25–28 (kind 4) has no effect but gives experience and disables the hand.
  - The CSB experience gain values and the 6-byte action sets go through the image (copy and conversion in `csbimage.c`), so `tables.c` needs no branch for them.
  - The dialog mouse tables are equal in CSB. The image copies them and moves the 8 pointers to the DM table addresses.
  - Not copied: `BUTTON_BORDER` and `BUTTON_INNER_BORDER` (only DM `endgame_draw_button` reads them; Step 8), and the string index tables (Step 3). Empty items 699 and 700 do not break loading: `load_strings` gives an empty list.
  - `main.c` keeps `csb_dir` in a file variable. `adventure_dir()` gives the folder of `g_adventure` for `--show`, `--view`, and the game.

### Step 3: CSB text

- `ui.c`: strings and action names from the APPB data in DM index order (`docs/csb-engine-diff.md` "Text"); object names from item 694 with the bit-7 terminator.
- The CSB texts that differ (disk messages, SAVE AND PLAY, SAVE AND QUIT, new texts) go through the same table.
- Tests: each DM text index gives the documented CSB string; the 33 changed object names (for example 23 STORM, 158 ANTIVENIN, 174 SHANK).
- Decisions made during the step:
  - New module `port/src/csbtext.c`: `csb_text_build` reads the APPB texts while the APPB module is loaded (`csb_image_build` calls it as its last step), so the port does not keep a copy of APPB. `ui.c` `load_strings` takes items 699 and 700 from `csb_text_item` for CSB. `tests/test_tables.py` builds `csbimage.c` alone, so its source list now also has `csbtext.c`.
  - The text rows in `csbtext.c` are by hand: single strings, pointer tables, the 26 disk message pointers, and the texts around a class name (spell failure 52, 54; level gained 62–68). The code references are in `docs/csb-engine-diff.md` "Text".
  - String index tables: entry k gets text index first + k. The class names and directions keep the CSB table order, so CSB text 2 is PRIEST, 3 WIZARD, 23 EAST, 24 SOUTH. Only these tables read texts 0–3 and 22–25.
  - Save dialog: texts 102 and 103 are SAVE AND PLAY and SAVE AND QUIT, at the places of the DM SAVE and QUIT buttons (as in the CSB dialog). Text 93 is empty. In CSB, the quit dialog of `startend.c` shows no message and a SAVE AND QUIT button, and the endgame QUIT button says SAVE AND QUIT. Steps 5 and 8 decide the CSB quit and endgame dialogs.
  - Every text index has a `TEXT_*` name in `port/src/ids.h` (coding standard rule 1). The file-local constants of `action.c` (`TEXT_FLIP_*`) and `magic.c` (now `TEXT_SPELL_FAILURE_*`) moved there. New names for Step 7: `TEXT_SPELL_FAILURE_MAGIC_MAP` (59, prefix empty, suffix " NEEDS A MAGIC MAP IN ACTION HAND FOR THIS SPELL."), `TEXT_NO_CREATURE` (107), `TEXT_CREATURE_NAME_FIRST` (108 + creature type, the CSB creature names).
  - `champion.c` reads its messages with `ui_string` (it read item 700 itself).
  - Texts 135–139 (memory errors) do not exist in CSB; `ui_string` gives "" for them.

### Step 4: CSB save file

- `savefile.c`: the CSB header variant (payload key at `0x3a`, fields 2 bytes later, 132 extra bytes, block 2 checksum check). Names `CSBGAME.DAT/.BAK`.
- `savegame.c`: champion bytes `0x118`–`0x11d` survive save and load; active groups 60 for a new CSB game and no minimum after a CSB load.
- Tests: `MINI.DAT` decodes with the port (same plain bytes as `tools/csb/csb_mini.py`); save and load of a CSB game give the same state; the original reader logic in `tools/csb/diff_test.py` accepts a file that the port writes.
- Decisions made during the step:
  - `savefile.c` selects the header by `g_adventure`: `field()` adds 2 to each DM field offset from `0x12a` on, `payload_key()` gives `0x14` or `0x3a`. CSB checks the block 2 checksum. New `save_header_extra_size()` gives 134 or 132; `savegame.c` copies that many extra bytes. The DM path writes the same bytes as before.
  - Champion bytes `0x118`–`0x11d`: new field `Champion.magic_map[6]` (raw record bytes) in `game.h`; `champion_pack` and `champion_unpack` copy it, for both adventures. The ctypes `Champion` structs in `tests/test_champion.py`, `tests/test_game.py`, `tests/test_ui.py` got the field (the struct size changed). Step 7 reads the bytes (`0x11c` is a big-endian word).
  - Active groups: `CSB_ACTIVE_GROUP_MAX_COUNT` 60 in `game.h`; `group_init_active_groups` uses it for CSB. `savegame.c` applies `MIN_ACTIVE_GROUP_COUNT` only for DM.
  - The port writes header byte 1 in CSB too (the merge of `CEDT.FTL` writes 2; Step 5 decides whether the merge result keeps 2).
  - `tests/test_csb_save.py`: `MINI.DAT` against `csb_mini.decode_save`; `MINI.DAT` load (map 4, x 22, y 18, direction 2, 11 maps, saved group count without minimum); round trip of the loaded game and of a new prison game; the original CEDT reader (`diff_test.check_decode`) accepts the port file; a damaged block 2 is rejected.

### Step 5: New adventure

- RESUME loads `CSBGAME.DAT`. NEW ADVENTURE starts the prison game.
- A save in the prison runs the merge in C (port of `tools/csb/csb_mini.py` `merge` and `encode_save`, from `CEDT.FTL` `0x105c7e` and `0x1085da`), writes `CSBGAME.DAT`, loads it, and continues.
- Save dialog: in CSB, SAVE AND QUIT (`TEXT_QUIT`) now goes to `confirm_quit` with an empty message and then to `endgame(0)` without a save. Step 5 makes SAVE AND QUIT save and then quit, and SAVE AND PLAY (`TEXT_SAVE`) save and continue. Step 5 also decides the quit-without-save dialog (text 93 is empty in CSB).
- The merge supplies the 132 CSB header extra bytes from `MINI.DAT` (`header_extra` in `savegame.c` is not reset on a new game). Step 5 decides whether the merged header byte is 2 (as `CEDT.FTL`) or 1 (as the port save).
- Tests: the C merge gives the same champions, header fields, and dungeon as the Python merge for the same party and random seed; an end-to-end test recruits champions in the prison, saves, and checks the party position in the CSB dungeon (map 4, x 22, y 18).
- Decisions made during the step:
  - The merge is `savegame_make_adventure` in `port/src/savegame.c`. It works on `Champion` structs (`reset_for_new_adventure`), not on record bytes, and packs them with `champion_pack` into the decoded `MINI.DAT`. The header part is `save_header_new_adventure` in `savefile.c`: payload bytes `0x100`–`0x127` are 0 (CEDT copies them from the saved game, and a port save has 0 there), game ID + 1, format 3, header byte 2 (as `CEDT.FTL`), then new keys and chain words. Later saves of the port write header byte 1 again (the CSB engine keeps the loaded byte; open issue below).
  - Random numbers: the port generator (`random16`) in the CEDT order: food, then water of each champion, then the 16 block keys, then the 127 chain words. `save_header_init` and the merge share `save_header_randomize`. The test feeds the C food and water values to `csb_mini.merge` and then compares all blocks, the portraits, the dungeon, and the header payload without keys and checksums.
  - The CEDT quirk of object bonuses (`0x104cca` removes the bonus from the saved game in slot 0, not from the copy) does not apply to a prison party: the prison champions come without objects, and the prison has no objects. The port does not remove a bonus either, so a party with a bonus object would keep the bonus as in CEDT. DM champion import stays out of scope.
  - The merged `CSBGAME.DAT` has no automap block. The load resets the automap; later advanced and turn-based saves add the block.
  - `save_current_game(&reason)` in `startend.c` is the save for both the dialog and the control socket: a plain save, or the merge in the prison (`g_adventure` CSB and `g_dungeon_id` 12, `CSB_PRISON_DUNGEON_ID` in `adventure.h`). After the merge it returns `SAVED_NEW_ADVENTURE` with the new adventure loaded. The caller starts it: SAVE AND PLAY and the socket `save` call `gameloop_start_loaded_game` (the GAME LOADED dialog); SAVE AND QUIT goes to `endgame(0)` at once, without the dialog (as the original). `MINI.DAT` comes from `gameloop_data_dir()/disk-b/MINI.DAT`; the file goes to the save folder.
  - Refused merge messages: "CAN'T MAKE NEW ADVENTURE WITHOUT CHAMPIONS." (CEDT shows "THE NEW ADVENTURE CAN ONLY BE MADE AFTER A SAVED GAME IS LOADED." for an empty party, which does not fit the port) and "EACH CHAMPION MUST HAVE A UNIQUE FIRST NAME!" (CEDT text). The control socket sends the same text as the error; a write failure keeps "cannot write the save file".
  - CSB save dialog (from `decomp-csb/A/APPB.c` `save_game` C`0x128cc0`, see `docs/csb-engine-diff.md` "Save and load"): CANCEL, SAVE AND PLAY, SAVE AND QUIT. The dialog closes after a save. SAVE AND QUIT calls `endgame(0)` after a successful save, without a question. A failed or refused save shows a dialog with OK and the game continues. `confirm_quit` is DM only.
  - `main.c` `start_csb`: the first NEW ADVENTURE or RESUME loads the CSB game files and runs `apply_mode` once (static flag). RESUME sets `mode` to `MODE_GAME` before `load_saved_game`, so the dialog clicks reach the command queue. A failed RESUME shows the CSB screen again (turn-based: the entrance picture; `load` and `new_game` over the socket start the game). The log line is `adventure csb, mode <name>`.
  - Step 1 open issue: `select_start_csb` sets `mode_given`, so after the first start Escape on the CSB screen does nothing. `apply_mode` runs only once.
  - After the credits (`g_return_to_entrance`), CSB shows the CSB screen; turn-based keeps the existing path (entrance picture, socket controls the next game).
  - Turn-based CSB and `DM_AUTO_ENTER`: `main.c` selects NEW ADVENTURE on the CSB screen after `plat_init`, as ENTER at the DM entrance. `new_game` over the socket loads `Dungeon.DAT` of the CSB folder (the prison) without a change in `control.c`.
  - Quick save and load need no change: `QUICK.DAT` is a plain CSB save, also in the prison.
  - Tests: `tests/test_csb_adventure.py` (12 tests). Existing tests needed no edit.
  - Open for later steps: header byte (`0x12c`) and dialog choice (`0x132`) of later port saves are 1, not the loaded byte and 0 for SAVE AND QUIT. The look of the RESUME dialogs on the CSB screen and of the entrance picture in turn-based CSB is not checked (manual test, Step 10).

### Step 6: Rule differences

- `action.c`: INVOKE, FLUXCAGE, FUSE do only the common part in CSB.
- `sensor.c`: sensor event priority 0; version checker limit 31.
- `champion.c`: CSB reincarnation rule.
- Tests: one scenario test per rule, both adventures.
- Decisions made during the step:
  - Checked in the APPB disassembly (`machine68k`): the switch table after C`0x126764` (key range 2–42, offsets relative to each entry) sends 3, 12, 26, 27, 35 and every key above 42 to the default C`0x126caa`. The default runs the common part in the port order (disabled ticks, stamina, experience, state redraw) and returns 1. Before the switch, CSB draws only the stamina random bit, as DM. `action.c` switches on `ACTION_NONE` for INVOKE, FLUXCAGE, and FUSE in CSB (`is_removed_in_csb`), so these actions also keep the full experience.
  - Sensors: C`0x121bc4` clears the priority byte; C`0x122766` compares the data with 31 (`sle`), DM K`0x11f052` with 36. `CSB_VERSION_CHECKER_LIMIT` 32 in `sensor.c` (the check is data < limit).
  - Reincarnation (C`0x1167e0`–`0x1168ca`): after the experience reset, statistics 1–6 (not luck): value = `max16`(minimum, current − current >> 3), written to current and maximum. Then `asr #2` on current and maximum health, stamina, and mana. Then the 12 points (`random16 % 7`, luck included), as DM. No random number in the CSB part.
  - No other rule difference in `docs/csb-engine-diff.md` needs a port change outside Steps 7–8 (the active group count is in Step 4; `group_steal_from_champion` never runs).
  - Tests: `tests/test_csb_rules.py` (20 tests, both adventures, private build). The dungeons have no free sensor record, so the version checker test moves a sensor of the map to an empty corridor square. No differential test against APPB in `dmtools.emu`: the emulator setup exists only for KAOS (`test_champion.World`), and a CSB setup is not small. The tests check the random seed instead: CSB INVOKE leaves the same seed as one `random_bit`.

### Step 7: Magic map

- First check whether the CSB dungeon has a scroll with the text "MAGICMAP". If not, document it and skip the step.
- Else: spells 25–28 (kind 4), timeline events 80–83, champion bytes `0x118`–`0x11d`, CREANAME and MAGICMAP in the scroll panel, the 7×7 map (`docs/csb-engine-diff.md` "Magic map").
- Tests: the spell needs the map in the action hand; events decrement the bytes; the panel draws the grid.

### Step 8: End of the game

- CSB `endgame`: THE END, RESTART THIS GAME for 900 frames, then the credits (graphic 5, CSB credits palette), then the CSB screen.
- Wall sensor type 18: the `ENDA.DAT` player (`docs/csb-data.md` "ENDA.DAT and the endgame", `decomp-csb/A/ANIM.c`), then the CSB screen.
- Tests: chunk walk over `ENDA.DAT`; first frame decodes; sensor 18 starts the ending.

### Step 9: LLM tools and docs

- `src/dmtools` (MCP server, `dm-play`): an `adventure` option, CSB save names, the state JSON says the adventure. `docs/llm-mode.md`, `docs/llm-playbook.md` (CSB start: recruit in the prison, then `save`).
- README: CSB data setup (`dm-extract` of both disks), the screens, `--adventure`.
- Tests: the control protocol starts a CSB game with `new_game` and answers `get_state`.
- Decisions: the tools only connect to a running game (socket), so no `--adventure` option in `dm-mcp` or `dm-play`; the start command takes `--adventure csb`. State JSON has top-level `adventure`. `dm-play --brief` shows `CSB` in the first line. Test: `tests/test_csb_tools.py`. README needed no change.

### Step 10: Full test

- Full test suite green. Manual test checklist for the user (selection screens, DM unchanged, CSB new adventure, save, resume, quick save, end). `CHANGELOG.md`. Merge to `main` only after the user's manual test.
