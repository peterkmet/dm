# Chaos Strikes Back support: implementation plan

Approved by the user on 2026-10-04 (design in chat, no PRD, as for the DM port). Branch: `feature/2026-10-04-csb-support`. Code style: `docs/coding-standard.md`.

## Goal

The C port plays Chaos Strikes Back (CSB, Amiga) from the user's own disks, in addition to Dungeon Master. A start screen in the DM font selects the adventure and the mode.

## Research

Read these documents before each step. They hold the addresses and the formats.

- `docs/csb-port-integration.md`: audit of the port, design of the selection screens.
- `docs/csb-engine-diff.md` and `docs/csb-appb-symbols.csv`: the CSB engine (`APPB.FTL`, disk A) against DM `KAOS.FTL`.
- `docs/csb-data.md`: CSB `Graphics.DAT`, `Dungeon.DAT`, save file, `ENDA.DAT`.
- `docs/csb-new-adventure.md`: `MINI.DAT`, the merge that builds `CSBGAME.DAT`. Prototype and differential test in `tools/csb/`.

## Decisions

- Data: `game/` stays DM. CSB disk A is in `game-csb/`, CSB disk B in `game-csb/disk-b/` (the disks have files with the same name and other content). Decompiled CSB modules: `decomp-csb/A/`, `decomp-csb/B/`. All are git-ignored. Tests that need CSB files skip when they are missing.
- Flow (user-approved):
  1. Adventure screen: DUNGEON MASTER / CHAOS STRIKES BACK. CHAOS STRIKES BACK is grey and cannot be selected when the CSB files are missing.
  2. Mode screen: VANILLA / ADVANCED / LLM. Escape goes back to the adventure screen.
  3. DM: the existing entrance. CSB: a text screen NEW ADVENTURE / RESUME / QUIT.
  - `--adventure dm|csb`. With `--adventure` and `--mode`, no selection screen. `--mode` alone means DM and no screen (existing scripts and tests keep working). `--adventure` alone shows the mode screen.
- The open decisions of `docs/csb-port-integration.md` take its proposals: Escape on the CSB screen goes back to the mode screen; Escape on the adventure screen does nothing; `--data DIR` is the disk A folder of the chosen adventure; the cursor does not wrap; the font comes from DM `Graphics.DAT`, else from CSB `Graphics.DAT`.
- Engine data: the port keeps its DM addresses. For CSB, `kaos_load` builds a KAOS-layout image from `game-csb/APPB.FTL`: it copies each table that the port reads from its CSB address to its DM address, and converts the tables with another layout (strides, split wall set ids, 6-byte action sets). The 25 files with `#define ... 0x10xxxx` do not change. Tables with other content or size (29 spells, experience gain) get an explicit CSB branch.
- New adventure: NEW ADVENTURE starts a new game in the CSB prison (`game-csb/Dungeon.DAT`, 24 mirrors). When the party saves in the prison (dungeon ID 12), the port merges the party into `MINI.DAT` (as `CEDT.FTL` does), writes `CSBGAME.DAT`, loads it, and the game goes on in the CSB dungeon. The original needs a restart with the utility disk; the port does not. Champion import from a DM save is out of scope.
- Copy protection: left out. The port acts as if every check passes.
- SAVE AND QUIT and the credits go back to the CSB screen, as the DM port goes back to the entrance.
- End of the game: wall sensor type 18 plays `ENDA.DAT`. If the animation format cannot be decoded completely, the step shows the decoded frames and documents the rest.
- Turn-based (LLM) mode: `new_game` over the socket starts NEW ADVENTURE (prison). The player recruits at the mirrors and calls `save`; the merge then happens as in the window.

## Steps

Each step ends with green tests (`make -C port`, `uv run pytest -q`), a review by the `reviewer` agent, and a commit. A fresh subagent executes each step. Mid-step decisions go into this plan or the research docs.

### Step 1: Adventure value and selection screens

- `port/src/adventure.c/h` and `port/src/select.c/h` as designed in `docs/csb-port-integration.md` (sections "The adventure value", "The selection module", "Argument parsing", "The game loop and the screen switch", "CSB entrance screen").
- `savegame.c` takes the file names from the adventure (`DMGAME.DAT/.BAK` or `CSBGAME.DAT/.BAK`). Quick save stays `QUICK.DAT`.
- Until Step 2 exists, NEW ADVENTURE and RESUME of CSB show "NOT AVAILABLE YET" on the CSB screen.
- Tests: `tests/test_select.py` (helpers, selection logic, drawing check, process exit codes). Existing tests stay green without edits.
- Decisions made during the step:
  - Font check: DM and CSB `Graphics.DAT` item 695 are the same 768 bytes. ASCII capitals (codes 65-90) draw correctly; `endgame_print_text` is not needed.
  - The CSB presence check uses the `--data` folder only with `--adventure csb`, else `game-csb/` (open decision 4 of `docs/csb-port-integration.md`). `build/dm --data game` does not disable CHAOS STRIKES BACK.
  - `start_adventure` loads the game data before `apply_mode` opens the control socket, so a load failure leaves no socket file.
  - `select_start_csb(message)` shows the CSB screen with an optional message line. `main.c` calls it with "NOT AVAILABLE YET" after NEW ADVENTURE or RESUME. The CSB screen and Escape stay in `MODE_SELECT`; `apply_mode` runs only when an adventure starts (DM entrance, or `--show`/`--view`).
  - `main` logs `adventure dm, mode <name>` when the DM entrance starts. The process tests use the line.
  - The screens use the system mouse pointer: the platform layer shows it until the game sets a pointer image.
  - Open for Step 5: after a CSB game ends, the CSB screen and Escape to the mode screen can change `g_game_mode` after `apply_mode` already ran (control socket open). Decide then whether Escape goes back to the mode screen after a game.

### Step 2: CSB engine image

- Data folder rule (decided after the Step 1 review): `--data DIR` sets the CSB folder only with `--adventure csb`. Without `--adventure`, `--data` applies to DM only, and CSB uses `game-csb/`. `main.c` computes the CSB folder once (`csb_dir`) and uses it for the presence check and for loading.

- `port/src/ftl.c` (or a new `port/src/csbimage.c`): with `g_adventure == ADVENTURE_CSB`, load `APPB.FTL` and build the KAOS-layout image. Use `docs/csb-engine-diff.md` "Data tables" and `docs/csb-appb-symbols.csv`. Generate the address list with a script under `tools/csb/` if that is simpler than writing it by hand; check the generated file in.
- `tables.c`: 6-byte action sets, CSB experience gain values, 29 spells (`SPELL_COUNT` per adventure).
- `gameloop_load_data` loads the CSB data folder. `--view` with `--adventure csb` shows the prison.
- Tests: every copied table equals the bytes at its CSB address; the tables that DM and CSB share have equal bytes in both images; the converted tables match the documented layout; `gameloop_load_data("game-csb")` succeeds; a new game in the prison renders the view without errors.

### Step 3: CSB text

- `ui.c`: strings and action names from the APPB data in DM index order (`docs/csb-engine-diff.md` "Text"); object names from item 694 with the bit-7 terminator.
- The CSB texts that differ (disk messages, SAVE AND PLAY, SAVE AND QUIT, new texts) go through the same table.
- Tests: each DM text index gives the documented CSB string; the 33 changed object names (for example 23 STORM, 158 ANTIVENIN, 174 SHANK).

### Step 4: CSB save file

- `savefile.c`: the CSB header variant (payload key at `0x3a`, fields 2 bytes later, 132 extra bytes, block 2 checksum check). Names `CSBGAME.DAT/.BAK`.
- `savegame.c`: champion bytes `0x118`–`0x11d` survive save and load; active groups 60 for a new CSB game and no minimum after a CSB load.
- Tests: `MINI.DAT` decodes with the port (same plain bytes as `tools/csb/csb_mini.py`); save and load of a CSB game give the same state; the original reader logic in `tools/csb/diff_test.py` accepts a file that the port writes.

### Step 5: New adventure

- RESUME loads `CSBGAME.DAT`. NEW ADVENTURE starts the prison game.
- A save in the prison runs the merge in C (port of `tools/csb/csb_mini.py` `merge` and `encode_save`, from `CEDT.FTL` `0x105c7e` and `0x1085da`), writes `CSBGAME.DAT`, loads it, and continues.
- Tests: the C merge gives the same champions, header fields, and dungeon as the Python merge for the same party and random seed; an end-to-end test recruits champions in the prison, saves, and checks the party position in the CSB dungeon (map 4, x 22, y 18).

### Step 6: Rule differences

- `action.c`: INVOKE, FLUXCAGE, FUSE do only the common part in CSB.
- `sensor.c`: sensor event priority 0; version checker limit 31.
- `champion.c`: CSB reincarnation rule.
- Tests: one scenario test per rule, both adventures.

### Step 7: Magic map

- First check whether the CSB dungeon has a scroll with the text "MAGICMAP". If not, document it and skip the step.
- Else: spells 25–28 (kind 4), timeline events 80–83, champion bytes `0x118`–`0x11d`, CREANAME and MAGICMAP in the scroll panel, the 7×7 map (`docs/csb-engine-diff.md` "Magic map").
- Tests: the spell needs the map in the action hand; events decrement the bytes; the panel draws the grid.

### Step 8: End of the game

- CSB `endgame`: THE END, RESTART THIS GAME for 900 frames, then the credits (graphic 5, CSB credits palette), then the CSB screen.
- Wall sensor type 18: the `ENDA.DAT` player (`docs/csb-data.md` "ENDA.DAT and the endgame", `decomp-csb/A/ANIM.c`), then the CSB screen.
- Tests: chunk walk over `ENDA.DAT`; first frame decodes; sensor 18 starts the ending.

### Step 9: LLM tools and docs

- `src/dmtools` (MCP server, `dm-play`): an `adventure` option, CSB save names, the state JSON says the adventure. `docs/llm-mode.md`, `docs/llm-playbook.md` (CSB start: recruit in the prison, then `save`).
- README: CSB data setup (`dm-extract` of both disks), the screens, `--adventure`.
- Tests: the control protocol starts a CSB game with `new_game` and answers `get_state`.

### Step 10: Full test

- Full test suite green. Manual test checklist for the user (selection screens, DM unchanged, CSB new adventure, save, resume, quick save, end). `CHANGELOG.md`. Merge to `main` only after the user's manual test.
