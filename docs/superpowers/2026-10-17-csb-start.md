# Chaos Strikes Back start by the stairs: PRD

Date: 2026-10-17. Branch: `feature/2026-10-17-options`. Status: implemented.

## Goal

In the advanced mode, a new Chaos Strikes Back (CSB) game goes: champion choice in the prison, then stairs down,
then the game starts in the CSB dungeon. One run, no disk switch, no utility screen, no save step
(`docs/todo.md:18-20`).

A claim without a `file:line` source is an assumption; the plan task that relies on it checks it first.

## The original

From `docs/csb/new-adventure.md` (sources: `reference/decomp/csb-a/`, `reference/decomp/csb-b/`):

1. Disk A, new game: the engine loads `Dungeon.dat`, the prison, dungeon ID 12. The player recruits champions at
   the mirrors (`docs/csb/new-adventure.md:9`, `33-35`).
2. The player saves: `CSBGame.dat` with dungeon ID 12 (`docs/csb/new-adventure.md:10`, `38`).
3. Disk B, the champion editor `CEDT.FTL`: LOAD CHAMPIONS, then MAKE NEW ADVENTURE. CEDT checks the saved game
   (format 3, dungeon ID 10 or 12, at least one champion, unique first names), loads `MINI.DAT` (a complete CSB
   saved game, dungeon ID 13), merges the champions into it and writes `CSBGAME.DAT`
   (`docs/csb/new-adventure.md:42-52`, `127-163`).
4. Disk A again, RESUME: the engine loads `CSBGame.dat` and plays the CSB dungeon (`docs/csb/new-adventure.md:14`).

- The merge resets each champion: full health, stamina and mana, no objects, food and water
  `1500 + (random & 0xff)`, statistics current = maximum, the minimum 30 (luck 10), the cells turned to the
  `MINI.DAT` party direction (`docs/csb/new-adventure.md:144-163`).
- The new adventure keeps from `MINI.DAT`: game time 469, random seed `0xa5349232`, the party on map 4 at
  (22, 18) facing south, the timeline, the groups and the dungeon. The game ID is the saved game ID + 1
  (`docs/csb/new-adventure.md:179-189`).
- The prison tells the player the steps: "THERE IS ONLY ONE LEVEL HERE. FIRST CHOOSE YOUR CHAMPIONS...THEN SAVE THE
  GAME...THEN RESTART WITH THE UTILITY DISK." (texts 24 and 25 of the prison; `docs/csb/new-adventure.md:16`).
- The prison has stairs. Read from `game-csb/Dungeon.DAT` with `dmcsb` (2026-10-17):
  - 2 maps. Map 0 (level 0, 20 x 16) holds the mirrors. Map 1 (level 1, 21 x 16, map offset (1, 3)) holds two
    rooms with 11 creature groups (creature types 10 and 7) and 4 stairs up.
  - Map 0 has 4 stairs down: (19, 3), (19, 7), (1, 15), (6, 15). Each stairs square is next to a door: (19, 2)
    and (1, 14) open, (18, 6) and (7, 15) closed with a button.
  - All 4 stairs lead to map 1. Map 1 has no stairs down and no exit to the CSB dungeon.
- Not traced: what map 1 is for, and whether the engine of disk A treats the prison stairs in a special way.
  Assumption: the stairs are plain stairs. The port plays the prison stairs with its normal stairs rules.

## The port today

  (`start_csb`, `src/platform/app.c:472-507`; `play_csb_intro`, `src/platform/app.c:288-296`).
- The port already has no disk switch: in the prison, a save makes the new adventure and the game goes on in it

  `src/engine/savegame.c:361-372`), decodes `disk-b/MINI.DAT` (`CSB_MINI_FILE`,

  `reset_for_new_adventure`, `src/engine/savegame.c:383-418`), encodes, writes `CSBGAME.DAT` (the old file becomes
  `CSBGAME.BAK`) and loads it with `savegame_load`.
- The CEDT merge is checked against the original routines (`tests/differential/test_csb_mini.py`,
  `tests/port/test_csb_adventure.py:98-104`).
- The stairs: the party steps onto stairs, `take_stairs` sets `g_session.new_party_map` and the place on the

  (`gameloop_tick`, `src/ui/gameloop.c:305-316`; `move_process_new_party_map`, `src/engine/move.c:364-384`).
  So today the prison stairs lead to map 1, as in the original.
- The turn-based protocol: `save` in the prison makes the adventure (`src/control/control.c:103-112`;
  `docs/manual.md:92`).

## Requirements

### The trigger

- The new adventure starts when all of these are true:
  - `g_session.mode == GAME_MODE_ADVANCED`;
  - `g_adventure == ADVENTURE_CSB` and `g_dungeon_id == PRISON_DUNGEON_ID`;
  - `g_session.new_party_map` is not -1, and its map level is one below the level of `g_party_map_index`: the
    stairs down from map 0 to map 1. The stairs up from map 1 to map 0 never start it;
  - `g_session.candidate_champion_index < 0`: a champion at a mirror that is not yet resurrected or reincarnated
    counts in `g_party_champion_count` (`src/engine/champion.c:426-428`), so a pending candidate stops the start.
- `gameloop_tick` checks the trigger before `move_process_new_party_map` (`src/ui/gameloop.c:310`) and calls one
  new `ui/startend` function.

### The start

- The `ui/startend` function calls one new engine function with the `MINI.DAT` path
  (`gameloop_get_data_dir()` and `CSB_MINI_FILE`, as `src/ui/startend.c:115`). The engine function:
  1. checks the party (no champion, first names not unique) as `savegame_make_adventure`
     (`src/engine/savegame.c:458-461`);
  2. reads and decodes `MINI.DAT` and merges the party (`merge_party`, unchanged). Up to here no game state
     changes; on a failure the function returns its reason;
  3. restores the merged state into the game (`restore_game`) without a file. `restore_game` frees the running
     dungeon first (`src/engine/savegame.c:571`), so a failed restore uses the snapshot rule of
     `savegame_load_from` (`src/engine/savegame.c:568-576`): the prison comes back;
  4. resets the automap (`explored_reset`) and sets the saved-game flag to false (`savegame_forget`):
     `restore_game` sets it true (`src/engine/savegame.c:521`).
- No file is written. The current save slot does not change.
- The game starts with `gameloop_continue_loaded_game` (`src/ui/gameloop.c:224-227`), without the GAME LOADED
  dialog. The party stands on map 4 at (22, 18) facing south. The start closes the inventory (`inventory_reset`,
  `src/ui/gameloop.c:143`) and sets `g_session.new_party_map` to -1 (`move_reset`, `src/ui/gameloop.c:147`,
  `src/engine/move.c:27-30`).
- After the start, `gameloop_tick` returns at once: it does not call `move_process_new_party_map` and does not run
  the rest of the tick, as after the endgame (`src/ui/gameloop.c:340-344`).

### A refused party

- When the engine function returns a reason, a dialog names it with OK: the texts of today
  (`src/ui/startend.c:117-127`), else UNABLE TO SAVE for an unreadable `MINI.DAT` or a failed restore. Then the
  stairs work as today: the party goes down to map 1.
- After a failed restore the snapshot holds the party position after `take_stairs`, and `restore_game` does not
  touch `g_session.new_party_map`. Assumption, checked first by the test: the next steps of the tick move the party
  to map 1 as today.

### Edge cases

- A sleeping party does not move: the sleeping input has no move command (`go_to_sleep`,
  `src/ui/command.c:700-712`).
- An open inventory does not stop the start; the start closes it.
- Assumption, checked first: the party cannot move while a candidate is open at a mirror. If it can, the trigger
  rule above keeps the stairs as today.
- The prison save of today stays in all modes: in the advanced mode the player can also save in the prison, and
  the save makes the adventure as today.

## Invariants

- Vanilla does not change. Gate: `g_session.mode == GAME_MODE_ADVANCED`.
- The `turnbased` mode and the LLM protocol do not change: the `save` in the prison stays the way
  (`docs/manual.md:92`); `g_advanced_features` is also true in `turnbased` (`src/ui/select.c:78`), so the gate is
  the mode, not that flag.
- The merge is the CEDT merge of today: the same champion reset, the same game ID + 1, the same `MINI.DAT` state.
- The dungeon data does not change; the prison texts stay.

## Decisions

- Why advanced only (owner decision below): the stairs rule removes map 1 of the prison, which the original and
  vanilla reach by the stairs, and advanced-only features leave vanilla unchanged. Vanilla already has no disk
  switch: the prison save makes the adventure (`docs/manual.md:83`).
- The trigger is the level change down, not a stairs square. Map 0 has no pits and no teleporters (read with
  `dmcsb`), and `g_session.new_party_map` is the one place that sees the change. The level check keeps the stairs up
  from map 1 out.
- MINI.DAT is decoded and merged before `restore_game`: a refusal or a bad file then changes no game state.
- No file: the stairs is not a save. Writing `CSBGAME.DAT` would replace the slot 1 game of the player without a
  question (`docs/superpowers/2026-10-17-save-slots.md`). The player saves when he wants.
- No intro and no dialog between the stairs and the game: the request is "stairs, then the game".
- On a refused party the stairs work as today. The party walks back up and fixes the party; no second rule for the
  position.
- The prison text "THEN SAVE THE GAME...THEN RESTART WITH THE UTILITY DISK" stays. It is dungeon data. The manual
  says what the advanced stairs do.
- The stairs start the dungeon only in the advanced mode; vanilla keeps the save in the prison (owner, 2026-10-17).
- In the advanced mode the party no longer reaches map 1 of the prison: it is a dead end with creatures and no exit (decided: acceptable).

## Risks

- Save compatibility: a save of the new adventure is a normal CSB save with dungeon ID 13, as today. The original
  CSB engine accepts the format (`tests/port/test_csb_save.py:119`). No new format.
- The dungeon of the game: after the stairs the game plays the dungeon of `disk-b/MINI.DAT`, not
  `game-csb/Dungeon.DAT`. `g_dungeon_id` becomes 13, so the prison music and the prison save rule end
  (`src/ui/music.c:82`, `src/ui/startend.c:113`). The data folder stays the CSB folder.
- Random numbers: food and water use the game random numbers of the prison (`src/engine/savegame.c:404-405`);
  CEDT uses its own generator (`docs/csb/new-adventure.md:165-167`). This is the behavior of today. After the
  restore the seed is the `MINI.DAT` seed `0xa5349232`, as in the original, so each new adventure starts with the
  same random numbers. The block keys of `randomize_header` (`src/engine/savefile.c:178-188`) still use
  `random16` in the merge (`savefile_make_adventure_header`), so the food and water values stay those of the save
  path; the keys have no effect without a file.
- The restore without a file: `savegame_load_from` also handles the automap block and the snapshot
  (`src/engine/savegame.c:551-587`). The new function must not skip a part that a load from a file does; the plan
  shares the code with `savegame_load_from` instead of a copy.
- Re-entrance: the hook runs inside the tick. The requirement "gameloop_tick returns at once" covers it, and the
  test checks it.

## Known consequences

- No save file after the stairs: THE END offers RESTART THIS GAME only after the first save, because it needs the
  saved-game flag (`src/ui/startend.c:424`).
- The stairs write no slot and do not change the current slot. A save of the prison that the player made before
  stays in its slot.
- In the advanced mode, map 1 of the prison is reached only by a refused party.
